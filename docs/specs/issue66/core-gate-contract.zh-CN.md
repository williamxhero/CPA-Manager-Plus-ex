# [SPEC 66-A] 独立自动门禁契约、协调与安全迁移

- 父规格：[#66](https://github.com/williamxhero/CPA-Manager-Plus-ex/issues/66)。本子规格不替代或缩减父规格。
- 状态：规划，未实现、未测试、未部署。GitHub 子 SPEC 链接见 [规划总览](./planning.zh-CN.md)。
- 归属：CPAMP-EX 定义契约、实现自身客户端及协调；core 的实现必须交目标项目上下文，经 cross-project-delegation 执行。本轮不发起实现。

### Use Case

管理员需要在本地 CPA 将额度自动暂停与手动关闭分离，并确认实际推理路由遵守独立门禁，而非只看到数据库或界面变化。

## Problem Statement

当前自动冷却修改与人工共用的 disabled。用户无法可靠区分手动意图与自动保护，恢复也可能误解历史停用原因。所检查的 core 没有独立、持久、带版本确认的自动门禁。只更新管理数据库、前端标志、模型注册表 suspension 或冷却到期时间，都不能保证新的推理尝试被排除。

## Solution

提供与人工状态正交的自动门禁：自动暂停阻止新推理尝试，但不终止已准入的在途尝试，不阻断额度查询。管理服务展示真实应用状态，缺能力或协调失败时明确显示不可用／待协调，而非“已保护”。恢复只解除本策略 owner 的暂停。

## User Stories

1. 作为管理员，我希望自动暂停不改变人工开关，以便保留手动意图。
2. 作为调用方，我希望暂停后的新请求、重试、故障转移和流式新尝试不再使用该资源，以便避免重复失败。
3. 作为 WS 调用方，我希望当前响应可完成而下一轮遵守暂停，以便兼顾在途请求与保护。
4. 作为管理员，我希望暂停中的资源仍可查询额度，以便充值或窗口恢复后解除暂停。
5. 作为管理员，我希望自动恢复只解除当前策略的暂停，以便不覆盖其他 owner、手动关闭和健康限制。
6. 作为管理员，我希望热加载和重启保留暂停，以便重启不产生短暂放行。
7. 作为管理员，我希望切换 CPA 实例或换账户后旧结果不会串到新资源，以便保护正确目标。
8. 作为维护者，我希望每次应用返回持久版本和运行确认，以便区分已提交、已生效和未知结果。
9. 作为管理员，我希望 core 不支持时明确得知保护不可用，以便不误以为界面状态就是路由状态。
10. 作为管理员，我希望历史原因不明的 disabled 保持原样，以免迁移误开启人工停用资源。
11. 作为维护者，我希望回退不能丢失门禁后静默放行，以便保持上线安全边界。

## Implementation Decisions

### 已核实事实与边界

- 所检查 core revision 为 `a4acc9f752bd46571f737a10c04bf413656ab06b`，不是 live 版本证明。现有手动状态、短期 cooldown、模型注册表 suspension 均不满足父规格。
- 新能力必须使用 v8 增量接口；保留旧管理状态 API，不扩展 v0 新功能。core 不理解金额，金额与证据判定归宿主管理服务。
- CPAMP 不能直接修改独立 core 仓库。Hermes 将本契约和验收交给该项目 owner，取回实际 revision、接口说明及测试证据；此处 issue 只记录消费端依赖，不冒充 core 已交付。

### 推荐契约（待目标项目实现确认，不能宣称已存在）

1. 能力发现返回独立能力版本 `independent_auto_suspension: 1`、运行模式、支持资源类型、路由路径覆盖、持久化和恢复就绪状态。版本号不能替代能力探测。
2. 管理端提供脱敏目标清单，含人工关闭的文件凭证和配置型 provider 行／Key；运行时未合成的手动关闭行也不能从清单消失。
3. 核心标识：持久 `instanceID`、不透明 `resourceID`、持久 `identityRevision`、删除重建 incarnation；provider 行另有成员集合版本。不使用名称、数组位置、executor 名或裸 auth_index 作为唯一持久绑定。
4. API 操作为读取能力、枚举目标、按目标及 owner 读取／更新 gate、按 operation ID 查询结果。具体 URL 与目标项目定案后回填同一 SPEC，不凭规划路径实现兼容假象。
5. 写入必须带 expected identity revision、expected gate revision、owner、operation ID、evidence ID；前置条件缺失拒绝，版本冲突 409。不复用重启后归一的 runtime Generation。
6. 多 owner 暂停取 OR。相同幂等键与相同内容返回原确认；同键不同内容拒绝。恢复只能解除本 owner，迟到恢复不能覆盖新暂停。
7. 仅当持久化与运行门禁均成功才确认 applied revision。超时或失败保留可查询的 operation 状态；CPAMP 记录 desired／durable／applied，进入待协调并幂等重试，不回退写 disabled。
8. 返回自动 gate 状态、手动状态和其他约束分开表达。gate 已清不等于无条件 effectiveEnabled=true；全局不可推导的资格显示未知，不伪造可路由。

### 执行、身份与恢复

- 选择器及每次新的上游推理尝试准入均检查当前 gate，涵盖 scheduler 快路径、legacy/plugin、同 Auth 401 刷新后重试、model pool、故障转移、流式、WS pin／下一轮及独立业务选择入口。
- ACK 定义明确的准入线性化点：该点之前已准入的尝试可完成，之后不能产生新的受限推理尝试；不能把整个 WS 连接都算作暂停前在途。
- token 刷新、冷却 reset、普通成功结果、配置重载及重新注册不得清 gate。身份变化使旧绑定失效；不能通过热加载间隙暂时放行。
- 启动先恢复持久 gate，再承接受影响推理流量。恢复失败不只打 warning 后继续放行；受影响目标保持 fail-closed／不就绪，范围必须可观察，不停掉无关资源。
- 受控管理员额度查询不走推理门禁；不能接受公共请求头伪造的“绕过 gate”。通用 api-call 不能直接被当作安全余额 API。
- 推荐首版以 standalone 作为能力声明起点，因为所检查 Home 使用额外调度。**这不是缩减当前实例验收**：Hermes 核实实际模式；若当前实例为 Home，必须补齐其路径或保留交付阻塞，不能把该实例排除。

### 兼容与历史迁移

- 保留 `codexQuotaCooldownEnabled`、环境锁及既有手动 API。禁用自动策略只停止新动作，不隐式清历史门禁；清除历史自动门禁需要明确独立操作。
- 仅 owner、目标身份及人工意图均可证明的旧记录可迁移。先确认独立 gate，再处理历史由自动逻辑写入的共用 disabled；操作期间并发人工关闭不能被迁移抹去。
- 原记录有歧义或迁移期间身份变化：保持旧停用，标为待确认。不能从“有 cooldown 记录”推断一定可恢复。
- 持久意图与 core 应用采用可重试协调，而非跨进程伪原子事务。默认单宿主协调 owner，租约避免重复执行；数据库失败与 core ACK 丢失均需恢复协议。

## Testing Decisions

主 seam 沿用父规格：管理 API → 真实管理服务／临时持久层 → 隔离真实 core → 合成协议上游。只替换外部网络、时钟和故障注入，不 mock 被验收选择器。复用现有 HTTP／SQLite、ownership、quota probe、core disabled／WS／持久化竞态测试的组织方式。

验收必须证明：

1. A/B 两资源暂停 A，所有已声明推理路径不再产生 A 的新尝试，B 正常；暂停前在途响应完成。
2. 同 Auth 401 重试、流式失败重试、WS 下一轮和 pin 不绕 gate；额度查询仍成功抵达 A 的来源。
3. 手动关与自动暂停并存；手动开不绕暂停，自动恢复不解除手动关／其他 owner；cooldown reset 不清独立 gate。
4. 包含 provider 多 Key、无 Key fallback、同协议不同配置行、配置重排及成员变更；不能串停其他行。
5. 身份／实例切换、同路径换账户、删除重建、迟到恢复和并发 CAS 均不串号；版本冲突和幂等冲突可观察。
6. 持久化／运行应用／启动恢复失败、ACK 超时与重试，不误报已保护、不短暂放行；热加载与重启门禁保留。
7. 迁移遇到未知 ownership、自动期间再次人工关闭、写失败可安全重试且无误恢复；降级不遗失保护。
8. 管理鉴权及合成秘密诱饵通过；未覆盖运行模式返回 unavailable，不能假定版本较新就支持。

## Out of Scope

本轮不实现 core、管理客户端或迁移，不访问 live，不修改其他仓库。此包不实现金额适配、全量刷新和 UI；不改变人工开关、优先级、插件 ABI 或健康策略。
